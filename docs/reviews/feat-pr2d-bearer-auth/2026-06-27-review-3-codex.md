# Review: `feat/pr2d-bearer-auth` vs `main` on 2026-06-27

## Findings

### 1. `AppleBridge/AppleBridgeApp.swift:11-24`, `AppleBridge/Models/ServerStore.swift:19-56`  
**State refresh is launched with unstructured `Task` blocks, which can race with `startServer()` / `stopServer()` and overwrite newer UI state.** `(swift-concurrency-pro)`

`AppleBridgeApp` now kicks off `Task { await serverStore.refreshBearerToken(); await serverStore.refreshStatus() }` from both `.onAppear` and `didBecomeActive`. `ServerStore` is `@MainActor`, but both `refreshBearerToken()` and `refreshStatus()` suspend on `await serverService...` before mutating `runState`, `lastError`, and `bearerToken`. That makes these refresh tasks reentrant relative to `startServer()`, which also mutates the same state across suspension points.

Why it matters: a foregrounding event can interleave with a start/stop operation and publish stale values back into the store. A concrete failure mode is `startServer()` setting `.starting`, then a queued refresh task observing the service as still stopped and resetting `runState` back to `.stopped` before startup completes. The same pattern can also resurrect stale `lastError` / `bearerToken` values.

Fix: serialize refreshes through one tracked task or one `refresh()` entry point, and avoid concurrent state writers for `runState`/`lastError`/`bearerToken`.

### 2. `rust/apple_bridge_core/src/auth.rs:11-20`, `rust/apple_bridge_core/src/config.rs:34-39`  
**`constant_time_eq()` exits early on length mismatch, so the bearer-token check is not actually constant-time for every valid configuration.** `(requesting-code-review)`

`constant_time_eq()` immediately returns `false` when lengths differ. At the same time, `validate_config()` only rejects empty bearer tokens; it allows arbitrary token lengths. That means request timing still reveals whether the attacker guessed the configured token length correctly.

Why it matters: this is an auth boundary, and the function is explicitly named `constant_time_eq()`. Fixed-length tokens generated by the Swift app reduce exposure, but the Rust API accepts externally supplied configs too, so the implementation does not match its security claim across supported inputs.

Fix: either enforce a fixed token format/length in config validation, or use a comparison that consumes both inputs without a length-based early return.

## Summary

1. Refresh work in `AppleBridgeApp` can race with server lifecycle operations and push stale state back into `ServerStore`.
2. The Rust bearer-token comparison leaks token-length information despite being presented as constant-time.
